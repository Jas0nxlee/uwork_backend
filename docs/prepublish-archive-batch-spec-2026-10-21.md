# 编译前归档批量删除联动

当前原 UI 的单条删除与“删除所有归档任务”使用不同接口；单条通过不代替批量接口。新增独立 profile，从本轮已完成任务的最后一条 assistant 回复经原 Fork 生成两个子任务，不发送新 prompt。分别归档两子任务，保留未归档父任务作为不应被删除的对照。

原归档列表“更多”→删除所有归档任务→确认框明确显示2项：取消时两子任务均保持 archived=1/deleted=0；再次打开并确认后两子任务 deleted=1，原 CLI 历史保留。父任务的可见元数据及消息/parts不变，仍可打开；刷新后两子任务不复活。全阶段真实模型请求和双方账本保持 baseline，不依赖直接调用批量API制造成功。

只使用新建隔离 fixture 的两个子任务。测试读取原 tasks-index/CLI SQLite，禁止直接写业务数据；保留原归档确认、批量选择收集、workspace RPC/事务、前端缓存刷新路径。原单条删除作为尾部回归保留。外部 MCP、网盘和发布安装包不在本例范围。

Fork准备阶段按原 `stable-fork-target` 合同可能补齐父 assistant 的 `anchor.productTurnId`，并为子任务增加隐藏 fork notice 与可见 timeline 各一条（四条继承消息之外共六条物理消息）。父任务批量删除基线在此合法准备完成后建立；此后归档/取消/批量确认/reload要求原始历史摘要不变。不得将 fork 的身份锚点补齐误报成批量删除修改历史，也不忽略删除阶段的任何变化。
