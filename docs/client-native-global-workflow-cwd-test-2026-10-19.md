# G05f 原生全局工作流「运行于」与 cwd/撤权验证（2026-10-19）

在真实 Electron Native 应用（动态工作流 alwaysOn 夹具）上，用**原界面**走完「保存工作流 → 提升为全局 → 在全局组用『运行于』选择已打开项目 → 运行」，并核对**运行实际使用的模型 cwd**与**运行历史记录的 cwd**一致，最后撤销文件系统权限复跑确认被拒。

**层次声明**：这是我自建的 CDP 探针（`scripts/tests/native-g05f-cdp-probe.py`，复用 G04k 的夹具/桥/守卫），不是仓库受审的 source-lock／Go／actor 流程，也没有 Root 独立复核。输入是 CDP `Input.dispatchMouseEvent` 与 `Input.insertText`，不是 OS 级输入。16 项检查、29 个原界面动作全部通过。

## 流程与实测结果

| 阶段           | 原界面动作                                                                                       | 实测结果                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| 前置策略       | 通过夹具既有配置命令发布当前企业策略（`allowFilesystem: true`）                                  | 见下「前置发现」                                                                                              |
| 进入工作流中枢 | 企业侧栏 agents 菜单（managed 模式下由原 `openAutomations` 所有者路由）→ 工作流页签              | 中枢为空态，存在「会话创建」入口                                                                              |
| 保存工作流     | 原「会话创建」入口 → 原 composer 输入 → 发送；原受控模型返回 `SaveWorkflow` 工具调用             | 请求带 32 个工具（含 SaveWorkflow）、流式                                                                     |
| 批准           | 原权限弹层选择「1. 允许」→ 确认                                                                  | 弹层写明落点 `<项目>/.zcode/workflows/native-ui-workflow.dwf.ts`                                              |
| 落盘           | —                                                                                                | 项目档定义 276 字节写入工作区                                                                                 |
| 提升为全局     | 卡片菜单 →「提升为全局」（原动作是**开会话让模型改写**，不是对话框）→ 追加受控指令 → 发送 → 批准 | 全局档定义 276 字节写入 `<HOME>/.uwork/workflows/`；全局组出现同一卡片                                        |

即：**实际模型 cwd = 历史 run.cwd = 通过「运行于」选择的已打开项目**，且撤权后同一入口被当前策略拒绝。

## 两个前置发现（都不是产品缺陷，是环境/路径事实）

1. **企业文件系统策略默认拒绝**。首轮保存工作流的工具结果是 `enterprise_filesystem_denied`——`security` 配置的 `allowFilesystem` 默认 `false`（`src/policy.ts`）。夹具自身不发布该配置，因此探针先用夹具既有的 `configure` 命令按管理员路径发布当前策略，再继续。这也解释了此前「模型工具调用成功但没有落盘」的现象。
2. **「提升为全局」是会话路径，不是对话框**。卡片菜单该项会打开一个新会话并预填提示，要求模型理解定义、去掉仓库依赖后用全局 scope 再次保存。因此探针走的是真实的两轮会话 + 两次原批准；为了让受控供应商能产出全局档，我给测试替身加了一个受控分支（消息含 `NATIVE_UI_WORKFLOW_GLOBAL` 时 `scope: "global"`，缺省仍是项目档）。这是测试替身的能力扩展，不改产品代码。

同一探针过程中还定位并修正了两处**我自己的**交互问题：投影里多写一个 `}` 导致脚本语法错误；卡片同名出现在项目组与全局组时唯一性查找返回空（改为按「是否在全局组内」分别取点）。

## 计量

本轮运行真实产生了模型调用（工作流运行本身就是要跑模型与子代理）：受控供应商共 10 次请求、后台账本 10 行全部 `settled`，运行历史显示该次运行 44 tokens。这些是**受控本机供应商**，不涉及真实厂商账单。
